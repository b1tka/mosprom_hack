# Инфраструктура и технологический стек

Документ для технических экспертов: что входит в систему, какая технология зачем выбрана и как компоненты связаны. Операционные детали (деплой, админка, статус проверок) — в `CLAUDE.md`.

## 1. Обзор

Чат-бот для мессенджера MAX автоматизирует онбординг нового сотрудника: ведёт его по сценарию адаптации, отвечает на вопросы по корпоративной базе знаний (RAG на локальной LLM), связывает с HR через обращения и следит за настроением, чтобы вовремя поднять тревогу.

Вся система поднимается одной командой Docker Compose (проект `onboarding`, сеть `onboarding-net`). Данные, LLM и персональные данные остаются в контуре компании: внешние облачные ИИ-сервисы не используются.

```
                    ┌────────────┐   HTTPS (long polling)   ┌─────────┐
   Сотрудник / HR ─►│  MAX API   │◄────────────────────────►│   bot   │
                    └────────────┘                          │ (Node)  │
                                                            └────┬────┘
        ┌───────────────┬───────────────┬──────────────┬─────────┼──────────────┐
        ▼               ▼               ▼              ▼         ▼              ▼
   ┌─────────┐    ┌──────────┐    ┌─────────┐    ┌──────────┐ ┌───────┐   ┌───────────┐
   │Postgres │    │ MongoDB  │    │  Redis  │    │    S3    │ │ Kafka │   │ ml (HTTP) │
   │ люди,   │    │ тикеты,  │    │ диалоги │    │ файлы,   │ │события│   │ RAG, LLM  │
   │ роли    │    │ статистика│   │         │    │ документы│ └───┬───┘   └─────┬─────┘
   └─────────┘    └──────────┘    └─────────┘    └──────────┘     │             │
                                                                  ▼             ▼
                                                        ┌──────────────┐  ┌──────────┐
                                                        │ml-mood-      │  │ Ollama   │
                                                        │consumer      │─►│ (LLM)    │
                                                        └──────────────┘  └──────────┘
```

## 2. Технологический стек и назначение

| Слой | Технология | Для чего |
|------|-----------|----------|
| Интерфейс | Мессенджер **MAX**, `@maxhub/max-bot-api` | Канал общения с сотрудником и HR: сообщения, кнопки, QR, вложения |
| Бот | **Node.js 22**, JavaScript (ESM) | Диалоги, роли и права, сценарий онбординга, тикеты, планировщик шагов |
| ML-сервис | **Python 3.12**, **FastAPI** | HTTP API для RAG, оценки настроения, разбора PDF, генерации тем тикетов |
| Векторный поиск | **ChromaDB** + эмбеддинги `intfloat/multilingual-e5-large` | Семантический поиск по базе знаний (top-3 фрагмента) |
| LLM | **meno-lite-0.1** (GGUF, `Q4_K_M`) в **Ollama** | Ответы по найденным фрагментам, классификация настроения, извлечение данных из PDF; работает локально на CPU |
| Реляционная БД | **PostgreSQL 16** | Пользователи, роли, теги, приглашения — данные со строгими связями |
| Документная БД | **MongoDB 7.0** | Тикеты с перепиской, состояние сценария, ответы опросов, статистика настроения |
| Кэш и состояние | **Redis 7** (AOF) | Шаг диалога каждого пользователя, антидубли и троттлинг уведомлений, журнал ошибок |
| Объектное хранилище | **S3** (OpenMaxIO, форк MinIO) | Документы базы знаний, входящие файлы, картинки |
| Шина событий | **Apache Kafka 3.9** (KRaft, 1 нода) | Асинхронная передача ответов и диалогов в оценку настроения, алертов — обратно в бота |
| Отчёты | Python, Яндекс SMTP | Регулярные письма HR и руководителям |
| Тестовая админка | FastAPI, Jinja2, HTMX | Только для тестирования и демонстрации |
| Оркестрация | **Docker Compose** (профили `llm`, `reports`, `admin`) | Воспроизводимый запуск всего стека |

## 3. Компоненты

### 3.1. Бот (`bot/`)
Единственная точка входа для пользователей. Принимает события MAX, определяет роль по `max_id` и ведёт нужный сценарий.
- **Роли:** новый сотрудник, руководитель подразделения, HR-менеджер, руководитель по подбору и развитию персонала.
- **Добавление сотрудника:** HR вводит данные (или присылает PDF — они извлекаются автоматически) и получает QR. Сотрудник сканирует его и подтверждает собственный номер через «Поделиться контактом». Токен приглашения хранится только в виде sha256-хэша, живёт 7 дней, одноразовый.
- **Сценарий онбординга:** декларативный `scenario.yaml` по ТЗ — шаги по расписанию от даты выхода (до выхода, первый день, 2 недели, 2 месяца, конец испытательного срока), опросы, ветки ответов, варианты по тегам (GTP, GrPP, Luzhniki). Планировщик внутри бота, состояние в MongoDB, поэтому рестарт ничего не теряет и не дублирует.
- **Вопросы сотрудника:** передаются в ML (`POST /v1/ask`), ответ приходит с кнопкой связи с HR.
- **Обращения к HR:** тикеты сотрудник ↔ закреплённый HR с перепиской, вложениями, архивом.
- **База знаний:** HR добавляет и удаляет документы прямо в чате.
- **Алерты:** читает топик `onboarding.alerts` и уведомляет HR о срочных ситуациях.
- Долгие операции (вызов LLM, индексация) выполняются в фоне, чтобы не блокировать приём сообщений для остальных пользователей.

### 3.2. ML-сервис (`ml/`)
Один образ, два процесса: HTTP API и Kafka-консьюмер.
- **RAG:** вопрос → эмбеддинг e5-large → поиск в ChromaDB → промпт с найденными фрагментами → LLM. Результат: ответ из базы, вежливый отказ на нерабочий вопрос или «ответа нет» (тогда бот предлагает передать вопрос HR).
- **Индексация:** документы (PDF, TXT, MD; сканы — через OCR) режутся на чанки и попадают в Chroma. Исходники лежат в S3 `knowledge/`.
- **Оценка настроения:** LLM классифицирует тональность, причину и срочность по вопросам сотрудника, ответам на опросы и полным диалогам закрытых тикетов. Результаты — в MongoDB (`stats` — сводка, `events` — история). При срочности публикуется алерт в Kafka.
- **Вспомогательные функции:** извлечение данных сотрудника из PDF, тема и категория тикета.
- Контракт API — `ml/README.md`, OpenAPI — `/docs`.

### 3.3. Хранилища
| Хранилище | Что лежит | Почему именно оно |
|-----------|-----------|-------------------|
| PostgreSQL | `users`, `role`, `tag`, `invites` | Связи (сотрудник → руководитель, HR, тег), ограничения целостности, транзакционная активация приглашения |
| MongoDB | `tickets`, `counters`, `onboarding`, `survey_answers`, `stats`, `events`, `admin_audit` | Гибкие вложенные документы: тикет вместе с перепиской, план шагов сценария, история оценок |
| Redis | `dialog:<max_id>`, `alert:<uid>`, `lastqa:*`, `bot:errors` | Быстрое эфемерное состояние диалога; переживает рестарт благодаря AOF |
| S3 | `knowledge/`, `incoming/` | Хранение файлов отдельно от БД; ML и бот обмениваются документами по ключу |
| ChromaDB | Векторный индекс базы знаний | Локальный embedded-индекс в томе `ml_data`, отдельный сервер не нужен |

### 3.4. Kafka
Развязывает бота и ML: бот не ждёт оценку настроения, ML не знает про MAX.

| Топик | Направление | Содержимое |
|-------|-------------|------------|
| `onboarding.answers` | бот → ML | ответ сотрудника на вопрос HR/опрос; полный диалог закрытого тикета |
| `onboarding.alerts` | ML → бот | `red_flag`: срочная ситуация, причина, объяснение LLM → уведомление закреплённому HR (не чаще раза в час на сотрудника) |

### 3.5. Аналитика и отчёты (`hr_analytics/`)
Читает `stats`/`events` из MongoDB и справочники из Postgres, строит отчёты по ролям (HR — ежедневно по будням, руководители — по понедельникам) и отправляет по почте.

### 3.6. Тестовая админка (`admin/`)
Веб-интерфейс для проверки и демонстрации: состояние всех сервисов, сотрудники и настроение, тикеты, база знаний, просмотр баз данных, управление шагами сценария. Доступна только через SSH-туннель, вход по одноразовому коду из бота. В промышленной эксплуатации не используется.

## 4. Ключевые потоки

**Вопрос сотрудника.** MAX → бот → `POST /v1/ask` → Chroma (поиск) → LLM → ответ → бот → MAX. Параллельно в фоне оценивается настроение.

**Красный флаг.** Вопрос / ответ опроса / закрытый тикет → Kafka `onboarding.answers` → консьюмер ML → LLM-оценка → запись в MongoDB → при срочности Kafka `onboarding.alerts` → бот → уведомление HR с кнопками.

**Добавление документа в базу знаний.** HR присылает файл → бот кладёт его в S3 `incoming/` → `POST /v1/documents` → ML режет на чанки, индексирует в Chroma, переносит в `knowledge/` → HR получает уведомление.

**Онбординг.** Активация QR → планировщик строит план шагов от даты выхода (MongoDB) → каждые 30 секунд выбирает созревшие шаги и отправляет их → ответы пишутся в `survey_answers`, негативные сразу уходят HR и в оценку настроения.

## 7. Безопасность и данные

- Секреты (токен бота, пароли) — только в `.env`, вне репозитория; в `.env.example` лежат заглушки.
- Приглашения: в БД только sha256 токена, срок 7 дней, одноразовость; активация проверяет, что контакт принадлежит самому сотруднику и номер совпадает с введённым HR.
- Доступ по ролям проверяется на каждом шаге диалога; HR видит тикеты своих сотрудников, руководитель по подбору — все.
- MongoDB: отдельный пользователь приложения с правом `readWrite` только на свою базу, root — для администрирования.
- Все данные и LLM работают в собственном контуре; наружу ходит только бот (MAX API, TLS с корневым сертификатом УЦ Минцифры) и SMTP для отчётов.
- Админка слушает только `127.0.0.1`, доступ через SSH-туннель, действия пишутся в журнал аудита.

## 8. Требования к ресурсам

| Компонент | RAM |
|-----------|-----|
| LLM meno-lite `Q4_K_M` (Ollama, CPU) | ~5–6 ГБ |
| Эмбеддинги e5-large в `ml` | ~1–2.5 ГБ |
| `ml-mood-consumer` | ~0.5 ГБ |
| Kafka, Postgres, Redis, S3, MongoDB, бот | ~1.5–2 ГБ |

С LLM — не меньше 12 ГБ RAM (рекомендуется 16 ГБ), без неё стек укладывается в 4–5 ГБ (тогда вопросы сотрудников остаются без ответов RAG, остальное работает). Диск: образ `ml` ~3.3 ГБ, модель эмбеддингов ~2.2 ГБ, LLM ~4.7 ГБ. GPU не требуется. Более лёгкая квантизация LLM (`IQ3_M`, 3.5 ГБ) подключается переменной `MENO_MODEL`.

## 9. Запуск

```bash
cp .env.example .env                  # указать BOT_TOKEN, поменять пароли
docker compose --profile llm up -d    # весь стек вместе с LLM
docker compose ps -a
```

Порядок развёртывания на новом сервере, миграции и проверка (`scripts/smoke.sh`) описаны в `CLAUDE.md`, раздел «Деплой на VPS».
