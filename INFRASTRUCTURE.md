# Инфраструктура бота онбординга (MAX)

Всё поднимается через Docker Compose (проект `onboarding`, сеть `onboarding-net`).

## Запуск

```bash
cp .env.example .env              # поменять пароли, указать BOT_TOKEN
docker compose up -d              # всё, кроме LLM
docker compose --profile llm up -d   # вместе с LLM (Ollama + meno-lite), нужно >= 12 ГБ RAM, см. «Ресурсы»
docker compose ps -a
```

Сброс данных (в т.ч. чтобы заново выполнились init-скрипты БД): `docker compose down -v`.

## Деплой на VPS

Пользователь развернул стек на VPS (с профилем `llm`). Свежие тома там пустые, поэтому после первого `up` нужно:
1. **Код:** `git pull && docker compose up -d --build ml bot` (после правок бота / ML).
2. **Миграции** (для БД, созданной до них; применять по порядку, каждую один раз):
   `docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < db/migrations/<файл>.sql`.
   Миграцию применять ДО пересборки бота, если новый код пишет в новые столбцы (например, `003_users_hr.sql` — без неё активация QR падает).
3. **HR-пользователь** (бот создаёт только `employee`; `max_id` — команда `/id` в боте):
   ```sql
   INSERT INTO users (name, surname, role_id, max_id)
   SELECT 'Евгений', 'Мерескин', id, 385032755 FROM role WHERE name = 'hr'
   ON CONFLICT (max_id) DO UPDATE SET role_id = EXCLUDED.role_id;
   ```
   Удобнее вставлять в интерактивный `psql` (`docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'`):
   многострочный heredoc при копировании в терминал зависал на `heredoc>`.
4. **База знаний:** без неё `/v1/ask` -> 503 «Векторная база пуста». PDF лежат в ветке `mood_find`:
   `git archive origin/mood_find data | tar -x` -> `docker compose run --rm -v "$PWD/data":/import ml python -m app.ingest upload /import`
   -> `docker compose stop ml && docker compose run --rm ml python -m app.ingest build --from-s3 && docker compose up -d ml` (~11 мин на CPU).
   Дальше документы добавляет HR через бота.
5. **Диагностика:** «Сервис ответов временно недоступен» у сотрудника = ML ответил ошибкой; причина — в `docker compose logs ml`
   (`Ошибка RAG` + traceback: пустая база, нет `ollama`, модель не скачана, таймаут). Ход индексации — `docker compose logs -f ml`.
6. **MongoDB только 7.0.** `mongod` 8.0.28+ / 8.3 не стартует на ядре Linux 6.19–7.0.13 (`MongoDB cannot start: ... known incompatibility`, SERVER-121912):
   в 8.x вшит Google TCMalloc (rseq), в 7.0 — gperftools, проверки нет. Не менять образ на `mongo:8`/`latest`. Том от 8.0 версия 7.0 не откроет:
   `docker compose down mongo && docker volume rm <проект>_mongo_data` (данных там пока нет), затем `docker compose up -d mongo`.
7. **Смоук после деплоя:** `./scripts/smoke.sh` (из корня проекта; `--no-llm` — без проверок модели, `--keep` — не удалять тестовые данные).
   Проверяет контейнеры, схему Postgres (миграции), версию Mongo, Redis/Kafka/S3, ML API, а с LLM — `/v1/ask`, `/v1/ticket-title`,
   запись оценки в `stats`/`events` и путь «диалог тикета -> Kafka -> консьюмер -> events»; затем логи бота и `hr-analytics check`.
   FAIL — стек неисправен (код выхода 1), WARN — на что обратить внимание (SMTP не настроен, пустая база знаний, LLM оценила мягче). Тестовый uid `00000000-0000-4000-8000-0000000005a0`, его записи в Mongo удаляются.

## Тестовая админка

Веб-интерфейс для **тестирования**: обзор системы, сотрудники и настроение, обращения, база знаний, управление базами. В проде не предполагается:
он показывает персональные данные и переписку, а SQL-консоль и редакторы дают **полный доступ к данным**.

**Включение**
1. В `.env`: `ADMIN_ACCESS` (`off` — выключена, `hr` — код входа только для `hr`/`hr_head`, `anyone` — любому, кто написал боту `/admin`),
   `SESSION_SECRET` и `ADMIN_API_TOKEN` (случайные строки: `openssl rand -hex 32`), при необходимости `ADMIN_URL`, `ADMIN_PORT`.
2. `docker compose --profile admin up -d --build admin bot` (бот нужен: он выдаёт коды и выполняет действия над тикетами).
3. С компьютера: `ssh -L 8080:localhost:8080 <vps>`, открыть http://localhost:8080. Порт публикуется строго на `127.0.0.1`
   (в compose зашито), поэтому без SSH-доступа к VPS сайт недоступен, даже если код входа получил посторонний.
4. Вход: написать боту `/admin`, ввести код (8 символов, 5 минут, одноразовый) или открыть ссылку из сообщения. Сессия 12 часов, cookie `HttpOnly`, `SameSite=Strict`.
   Десять неверных кодов с одного адреса блокируют вход на 10 минут.

**Разделы**
- *Обзор*: состояние Postgres, Mongo, Redis, Kafka (с лагом групп), S3, ML, LLM, бота; счётчики; красные флаги; настроение за 7 дней; последние ошибки бота
  (бот пишет `console.error` в Redis-список `bot:errors`, последние 100).
- *Сотрудники*: список с риском и индексом настроения (расчёт из `hr_analytics/app/analytics.py`), карточка с динамикой и тикетами; действия: снять красный флаг,
  закрепить HR, изменить email.
- *Тикеты*: фильтры и поиск, переписка; ответить сотруднику, закрыть, переоткрыть (через **внутренний HTTP бота** `bot:3001`, секрет `ADMIN_API_TOKEN`, порт не публикуется:
  отправка в MAX, уведомления и диалог в Kafka работают как при кнопках в боте), переназначить HR.
- *База знаний*: список, загрузка (S3 `incoming/` → `POST /v1/documents` в фоне), удаление, тестовый вопрос к RAG от тестового uid `00000000-0000-4000-8000-0000000000ad`.
- *Базы данных*: Postgres (таблицы, поиск, правка и удаление строк по первичному ключу, SQL-консоль на один запрос за раз), Mongo (коллекции, фильтр JSON без `$where`,
  редактор документов, вставка, удаление документа и коллекции), Redis (поиск по маске, значения, удаление; значения сессий и кодов входа скрыты), Kafka (только чтение:
  топики, смещения, последние сообщения), S3 (список, скачивание, удаление).

**Безопасность.** Любое изменение или удаление в базах и любой изменяющий SQL требуют ввода слова `ПОДТВЕРЖДАЮ`; удаление коллекции Mongo — ещё и её имени.
Все изменяющие запросы защищены CSRF-токеном, принимается только `Host: localhost|127.0.0.1` (защита от DNS-rebinding), сервис не стартует без `SESSION_SECRET` от 32 символов.
Каждое действие пишется в Mongo `admin_audit` (кто, что, когда; тексты SQL до 2000 символов). Подтверждение защищает от случайного клика, а не от умысла:
SQL-консоль выполняет любой запрос с правами пользователя Postgres из `.env`.

**Как убрать.** `docker compose --profile admin down`, в `.env` поставить `ADMIN_ACCESS=off` (или удалить `ADMIN_*`, `SESSION_SECRET`) и пересоздать бота (`docker compose up -d bot`):
команда `/admin` ответит «Админка отключена», внутренний API бота не поднимется без `ADMIN_API_TOKEN`. Полное удаление из кода: каталог `admin/`, сервис `admin` в `docker-compose.yml`,
`bot/src/admin.js`, `bot/src/internal.js` и их подключение в `bot/src/index.js`.

**Проверка.** Юнит-тесты: `docker run --rm -v "$PWD/admin/tests:/srv/tests:ro" -e ADMIN_ACCESS=anyone -e SESSION_SECRET=$(openssl rand -hex 32) onboarding-admin python -m unittest discover -s tests`
(после `docker compose --profile admin build admin`). `./scripts/smoke.sh` при запущенной админке проверяет loopback-порт, вход по коду и открытие всех разделов.

## Сценарий онбординга («Корсик»)

Бот ведёт нового сотрудника по сценарию из ТЗ (`Финал. ТЗ. Чат-бот Корсик- 15.09.xlsx`): знакомство до выхода, первый рабочий день по часам,
3-й день, 2 недели, 2 месяца, окончание испытательного срока, опросы, поздравления, подборки. Вопросы боту можно задавать на любом этапе.

**Где что лежит**
- `bot/src/scenario/scenario.yaml` — весь сценарий (тексты из таблицы дословно, `Х` заменён на `{name}`): шаги, время, теги, картинки, кнопки, ветки ответов. Формат описан в шапке файла.
  Правка текста или времени = правка файла + `docker compose up -d --build bot`. Ошибка в файле: бот не стартует и перечисляет все проблемы (`docker compose logs bot`).
- `bot/src/scenario/load.js` (проверка и компиляция), `schedule.js` (расписание), `bot/src/onboarding/` (движок, планировщик, отправка, уведомления HR).
- `bot/assets/photos/<N>.jpg` — картинки «Изображение N» из ТЗ. `bot/assets/content/` — необязательные файлы-вложения (README внутри): PDF, презентация, открытки; нет файла — сообщение уходит без него.
- Mongo: `onboarding` (план шагов и состояние диалога на сотрудника), `survey_answers` (все ответы). Postgres: `users.start_date`, `invites.start_date` (миграция `004`).

**Расписание.** Время считается от QR: дата выхода = дата генерации QR + 3 дня (выходной -> понедельник), запоминается в приглашении и копируется в `users.start_date`.
Часовой пояс Москва (+3). Рабочие дни — Пн–Пт без праздников; «второй/третий рабочий день» по будням; «через 10 дней», «через 2 недели» — календарно (выходной -> понедельник);
«первый день второго месяца» = дата выхода + 1 месяц; «+1 мес. 2 нед.», «+1 мес. 3 нед.», «+2 мес. 2 нед.»; «последний день испытательного» = выход + 3 месяца − 1 день (выходной -> пятница).
Время, которого нет в ТЗ (за день до выхода, +10 дней, +2 недели и т. п.), выставлено в `scenario.yaml` (12:00 / 10:00) и правится там же.
Активация QR запускает сценарий сразу (шаги «за 2-3 дня до выхода»). Если сотрудник активировал QR поздно, шаги, чьё время ушло меньше чем на сутки, уходят сразу, старые пропускаются.
Планировщик в процессе бота, проход каждые 30 с; состояние в Mongo, поэтому рестарт ничего не теряет и не дублирует (шаг захватывается атомарно, у сотрудника идёт один шаг за раз).

**Теги.** Офис — GrPP и Luzhniki (`office_tags`), GTP — предприятие. Шаги и узлы с `tags:`/`office:` уходят только подходящим (карта территории — GTP, карта этажей — Luzhniki,
«первый день позади», адаптационный план, книги — только офис, спортзал — GTP, мероприятия — GrPP и Luzhniki; варианты текстов документов, транспорта, справочника, опроса).

**Вопросы и ответы.** Типы: выбор (в т. ч. «Свой вариант»), множественный выбор, шкала 1–10 (ниже 8 просит причину), да/нет с причиной, свободный текст (рассказ о себе + фото).
Вопрос заменяется на «✓ ответ», повторное нажатие даёт «уже закрыт». Вопрос «ты/вы» запоминается (`onboarding.address`), тексты одинаковые; без ответа за 12 ч берётся «ты».
Опрос без ответа напоминает через сутки и ещё раз через сутки (картинка 12), затем считается просроченным.
Когда бот не ждёт ответ, любой текст сотрудника идёт в RAG, как раньше; когда ждёт текст (причина, «свой вариант», рассказ), текст — это ответ. Ответы кнопками работают всегда.

**HR и негатив.** Негативный ответ (в `scenario.yaml` пометка `negative: true`, шкала ниже 8, «Нет» по доступам, «отстаю», «задумываюсь об уходе») сразу уходит закреплённому HR
(нет закреплённого — всем hr/hr_head) с кнопкой «Написать сотруднику»; причина — отдельным сообщением. Тексты ответов и причины идут в Kafka `onboarding.answers`
(`hr_question` = вопрос, `answer` = ответ, `stage` — этап по дням от выхода: `preparing_for_start_job`, `first_adaptation_days`, `beggining_of_adaptation`, `main_adaptation_part`, `completion_of_adaptation`) в оценку настроения.
Кнопки в сообщениях: «Связаться с рекрутером» = чат с закреплённым HR (тикет, тот же, если уже открыт), «Передать проблему в отдел подбора персонала» = бот просит описать проблему, текст становится тикетом.
Команды сотрудника: `/HR`, `/Food`, `/menu` (там же «Связаться с HR», «Где пообедать»). Рассказ о себе (2-й день) и интерес к материалам без ответа в базе знаний уходят HR.
Ответы «Да» на предложения без текста в ТЗ (транспорт, карта, спортзал) берутся из базы знаний (RAG) по фиксированному вопросу; если ответа нет, сотрудник получает fallback, HR узнаёт об интересе.
Приветственное письмо (строка 19) уходит на `users.email` через Яндекс SMTP (`SMTP_*` в `.env`, как у `hr-analytics`); без SMTP шаг пропускается с записью в лог.

**Добавление сотрудника из PDF.** HR присылает боту PDF с данными нового сотрудника (анкета, карточка, приказ, формат любой; один файл — один человек). Если PDF пришёл вне шага диалога,
бот спрашивает: «Добавить сотрудника» / «Добавить в базу знаний» / «Ничего»; кнопка «Добавить сотрудника из PDF» в `/menu` сразу ждёт файл. Дальше бот в фоне скачивает PDF и отправляет в ML `POST /v1/users/extract`
(модуль из ветки `pdf_user_load`, подробности в `ml/README.md`), сопоставляет тег с таблицей `tag` и руководителя с руководителями из БД (по фамилии, с учётом склонений) и открывает обычную форму добавления:
известные поля пропускаются, недостающие (тег, руководитель, почта, телефон) бот спрашивает кнопками и текстом, HR проверяет карточку и нажимает «Создать» — появляется приглашение с QR и датой выхода.
Телефон нормализуется, номер, уже занятый в системе, останавливает добавление. Без LLM распознавание недоступно (бот предложит добавить вручную). Код: `bot/src/pdfusers.js`, `bot/src/pdfusers/match.js`.

**Меню HR «Мои сотрудники»** (`/menu`): свои сотрудники (hr_head — все) со статусом и прогрессом; карточка: изменить дату выхода (ДД.ММ.ГГГГ, расписание пересчитывается), пауза/продолжить, запустить сценарий (для сотрудников, заведённых до внедрения).
**Админка, раздел «Онбординг»:** шаги и их состояние, ответы опросов, «выполнить следующий шаг сейчас», сдвиг будущих шагов на N дней, пауза, пересчёт даты, запуск и сброс. Так проверяются 3 месяца сценария за минуты.

**Деплой.** Миграцию `004` применить ДО пересборки бота (бот читает `users.start_date`), затем `docker compose up -d --build bot`
(пересобирается образ: добавлены `assets/` и зависимости `yaml`, `nodemailer`). Сотрудников, заведённых раньше, запускает HR кнопкой «Запустить сценарий» или админка.

**Проверка.** `cd bot && npm test` (юнит: расписание, загрузчик и валидатор сценария); `npm run test:int` (нужны Mongo и Redis, `MONGO_URL`, `REDIS_URL`): сотрудник проходит все 3 месяца на поддельных часах
(GrPP и GTP), негатив, причины, множественный выбор, рассказ о себе, напоминания, таймаут «ты/вы», поздняя активация, пауза, смена даты, рестарт без дублей. Живую доставку картинок и кнопок в MAX
нужно пройти руками: создать приглашение, активировать, нажать кнопки, затем в админке «выполнить следующий шаг сейчас» по очереди.

### MongoDB
Хранит обращения сотрудников к HR (тикеты), пишет и читает бот (`bot/src/mongo.js`, `bot/src/tickets.js`):
- `tickets` — тикет вместе с перепиской (`messages`), схема в комментарии `tickets.js`. Индексы (создаёт бот при старте):
  `number` (уникальный), `{hrId, status, lastMessageAt}`, `{status, lastMessageAt}`, `{employee.id, status, lastMessageAt}`;
- `counters` — сквозной номер тикета (`{_id: 'tickets', seq}`).
- Root-пользователь (`MONGO_ROOT_USER` / `MONGO_ROOT_PASSWORD`) — только для администрирования.
- Пользователь приложения (`MONGO_APP_USER` / `MONGO_APP_PASSWORD`) с ролью `readWrite` только на базу `MONGO_DB` (`onboarding`);
  создаётся `db/mongo-init/01_app_user.js` при первом старте тома `mongo_data` (повторно не выполняется, как `db/init` у Postgres).
- Сервисам `bot`, `ml`, `ml-mood-consumer` compose передаёт `MONGO_URL=mongodb://<app_user>:<pass>@mongo:27017/onboarding`.
- Консоль: `docker compose exec mongo mongosh -u <root> -p <pass>`.

### S3 / OpenMaxIO
OpenMaxIO — форк веб-консоли MinIO, отдельного образа сервера нет. Образы MinIO на Quay и
Docker Hub не скачались (401 / access denied), поэтому использован неофициальный
`ghcr.io/snazy/maxio-release` (MinIO + mc + консоль OpenMaxIO). Проект-источник, судя по
новостям, не развивается. Образ меняется переменной `S3_IMAGE` в `.env`.
Бакет по умолчанию: `onboarding-files`.

### ML-сервис (`ml/`)
Код ML-команды из веток `ml_ai` -> `mood_find` перенесён в `ml/` (не git merge: ветка `mood_find` удаляла наши
`docker-compose.yml`, `db/` и доки). Ветки `ml_ai`, `mood_find`, `hr_analytics` остаются на сервере как история;
дальнейшая ML-разработка — в `ml/` от `main`. Подробно: `ml/README.md`.

- **RAG**: вопрос -> поиск в Chroma (эмбеддинги `intfloat/multilingual-e5-large`, top-3 чанка) -> LLM meno-lite-0.1 (через Ollama) -> `(код, ответ)`.
- **Настроение**: классификация mood / reason / urgent той же LLM; статистика в Mongo (`stats` — сводка на сотрудника, `events` — история оценок).
  Источники: каждый вопрос из `/v1/ask` (в фоне, после ответа), ответы на вопросы HR и **полные диалоги закрытых тикетов** из Kafka `onboarding.answers` (один вердикт на диалог).
- **База знаний**: исходные документы в S3 `onboarding-files/knowledge/`, векторная база Chroma и `knowledge_base.json` — в томе `ml_data`,
  кэш моделей HuggingFace — в томе `hf_cache`. Полная переиндексация вручную: `docker compose run --rm ml python -m app.ingest build --from-s3`.
  Отдельный документ HR добавляет через бота (`/menu` -> «Добавить файл в базу знаний», см. раздел «Бот»).

Контракт:
- `POST /v1/ask`, тело `{"user_id": "<users.id>", "question": "<строка>", "stage": null}` -> HTTP 200, тело `{"code": 200 | 400, "answer": "<строка>"}`.
  `code: 200` — ответ из базы или вежливый отказ на нерабочий вопрос; `code: 400` — рабочий вопрос, но в базе ответа нет.
- `503` — LLM или векторная база недоступны (в т.ч. база пуста или профиль `llm` не запущен); `422` — невалидный запрос.
- `POST /v1/documents`, тело `{"key": "incoming/<id>/<имя.pdf|.txt|.md>"}` — ML скачивает файл из S3, режет на чанки (OCR для сканов),
  добавляет в Chroma и `knowledge_base.json` (одноимённый документ заменяется) и переносит файл в `knowledge/<имя>`.
  Ответ 200 `{"source", "chunks_added", "replaced"}`; 400 — неверный ключ/формат или текст не извлёкся (входящий файл удаляется);
  404 — нет файла в S3; 503 — сбой S3 или Chroma. Синхронный, может идти минуты; документы индексируются по одному (блокировка в процессе).
- `GET /v1/documents` -> `{"documents": [имена]}` (проиндексированные + лежащие в S3 `knowledge/`);
  `DELETE /v1/documents/{имя}` — удаляет из `knowledge_base.json`, Chroma и S3; 404 — документа нет. Ждёт ту же блокировку, что индексация.
- `GET /v1/stats/{user_id}`, `GET /health`; OpenAPI: http://localhost:8000/docs
- Бот не зависит от `ml` при старте; таймаут запроса 90 с (`ML_TIMEOUT_MS`): LLM до 60 с (`LLM_TIMEOUT`) + поиск.

### Ресурсы
| Компонент | RAM |
|-----------|-----|
| LLM meno-lite-0.1 `Q4_K_M` (Ollama, CPU) | ~5–6 ГБ (4.65 ГБ веса + контекст) |
| эмбеддинги e5-large в `ml` | ~0.9 ГБ в простое (замер), до ~2.5 ГБ под нагрузкой |
| `ml-mood-consumer` | ~0.5 ГБ |
| Kafka, Postgres, Redis, S3, бот | ~1.5–2 ГБ |

С LLM нужно **не меньше 12 ГБ RAM** для Docker (рекомендуется 16 ГБ). Легче: `MENO_MODEL=hf.co/bond005/meno-lite-0.1-gguf:IQ3_M` (3.54 ГБ).
Без профиля `llm` стек занимает ~4–5 ГБ. На dev-ноутбуке (8 ГБ для Docker) LLM не запускается.
Диск: образ `ml` 3.25 ГБ (torch CPU, easyocr), модель эмбеддингов 2.2 ГБ (том `hf_cache`), LLM 4.65 ГБ (том `ollama_data`).

Первый старт `ml` скачивает e5-large (~2.2 ГБ); на медленной сети (~1 МБ/с) это ~40 минут, healthcheck на это время показывает
`unhealthy` — это не ошибка. Протокол Xet у HuggingFace на такой сети зависал, поэтому в compose `HF_HUB_DISABLE_XET=1`.
Индексация 4 PDF (`ingest build --from-s3`) на CPU заняла ~11 минут: скан на 23 страницы распознаётся OCR. Во время индексации `ml` лучше
остановить (`docker compose stop ml`), затем `docker compose up -d ml`.

### Kafka
Топик `onboarding.answers` (3 партиции, RF 1, имя — `KAFKA_TOPIC_ANSWERS`): ответы сотрудников на вопросы HR
`{uid: users.id, hr_question, answer, stage}`, ключ = `uid`. Пишет бот (`sendHrAnswer` в `bot/src/kafka.js`; опросы HR в боте
пока не реализованы), читает `ml-mood-consumer`. Старые топики `ml.requests` / `ml.responses` больше не используются
(в уже созданном брокере остались, на работу не влияют).

### Уведомления HR о срочных оценках (red_flag)
ML при `urgent=true` пишет алерт в Kafka-топик `onboarding.alerts` (создаётся `kafka-init`, имя в `KAFKA_TOPIC_ALERTS`). Бот читает его консьюмером
(`bot/src/alerts.js`, группа `onboarding-bot-alerts`, стартует вместе с ботом; при сбое Kafka повторяет подключение каждые 30 с, бота не роняет)
и отправляет сообщение **закреплённому HR** (`users.hr_id`); если он не закреплён — всем `hr` и `hr_head`. По одному сотруднику — не чаще раза в час
(Redis `alert:<users.id>`). В сообщении: ФИО, тег, руководитель, тема, объяснение LLM, источник (вопрос боту или обращение №N), кнопки
«Открыть обращение» (для тикета) и «Флаг обработан». Кнопка пишет в Mongo `stats.red_flag=false`, `last_reason=""`, `red_flag_reset_at/by`
и снимает троттлинг. Сбросить может закреплённый HR (и любой HR, если HR не закреплён) и `hr_head` (любого сотрудника).
Для работающего брокера топик создаётся командой `docker compose up -d kafka-init`; ML-продюсер при отсутствии топика создаст его сам (автосоздание Kafka).

### Настроение и отчёты
ML пишет статистику в Mongo (`STORE_BACKEND=mongo`): `stats` (сводка на сотрудника) и `events` (история), формат — в `ml/README.md`.
`hr_analytics/` (из ветки `mood_find`) читает эти коллекции и `users`/`role`/`tag` из Postgres и шлёт отчёты: `hr` — каждый будний день в 09:00,
`director` и `hr_head` — по понедельникам (cron в `SCHEDULE_*`). Письма уходят на `users.email`; у HR, директоров и `hr_head` он пуст,
пока не проставлен вручную (`UPDATE users SET email = '…' WHERE max_id = …`), иначе отчёт пропускается с предупреждением в логе.

Включение (сервис в профиле `reports`, сам не стартует):
1. В `.env`: `SMTP_USER`, `SMTP_PASSWORD` (пароль приложения Яндекса, не пароль аккаунта), `REPORT_RECIPIENT_OVERRIDE=<свой адрес>` — все письма идут туда с пометкой `[TEST]`.
2. Проверка: `docker compose --profile reports run --rm hr-analytics python -m app check`, затем `... python -m app preview` (HTML+PDF в контейнере, без отправки) и `... python -m app send --role hr`.
3. `docker compose --profile reports up -d --build hr-analytics`. Когда отчёты проверены — очистить `REPORT_RECIPIENT_OVERRIDE` и пересоздать сервис: письма пойдут реальным получателям.
Старые ключи Redis `onboarding:stats:*` не используются и не переносились.

## База данных

Таблицы: `role`, `tag`, `users` (по UML) и `invites` (приглашения сотрудников, добавлена позже).

- `users.role_id → role.id` — `RESTRICT`
- `users.tag_id → tag.id` — `SET NULL`
- `users.director_id → users.id` — `RESTRICT` (NULL у руководителей)
- `users.max_id` — `bigint`, `UNIQUE NOT NULL`
- `users.email`, `users.phone` — `varchar`, nullable, без проверки формата и уникальности (добавлены миграцией `db/migrations/001_users_email_phone.sql`)
- индексы: `director_id`, `role_id`
- триггер `users_set_updated_at` обновляет `updated_at` при `UPDATE`

Сиды:
- `role`: `employee` (новый сотрудник), `director` (руководитель подразделения),
  `hr` (HR-менеджер), `hr_head` (руководитель по подбору и развитию персонала).
  Слаги — предположение, в UML были только `employee | director`.
- `tag`: `GTP`, `GrPP`, `Luzhniki`.

### Таблица `invites`
Приглашение, по которому сотрудник станет записью в `users` (до активации его `max_id` неизвестен, поэтому отдельная таблица).

| Поле | Описание |
|------|----------|
| `token_hash` | `sha256(токен)`, `UNIQUE`; сам токен только в QR/ссылке |
| `name`, `surname`, `tag_id`, `director_id`, `email`, `phone` | данные, введённые HR (`phone` только цифры, `7XXXXXXXXXX`) |
| `created_by` | `users.id` HR, создавшего приглашение (`ON DELETE CASCADE`) |
| `expires_at` | считается в БД: `now() + 7 дней` |
| `used_at`, `used_by_max_id` | заполняются при активации |

## Бот (`bot/`)

JS (ESM, Node >= 20), библиотека `@maxhub/max-bot-api`. Токен: `BOT_TOKEN` в `.env`.

| Файл | Что делает |
|------|-----------|
| `src/index.js` | `/start`, `/id`, вопросы сотрудников -> ML API, запуск и остановка |
| `src/config.js` | чтение env (дефолты для запуска с хоста) |
| `src/db.js` | пул Postgres, `findUserByMaxId`, `findEmployeeContacts` (закреплённый HR, руководитель), `listTags`, `listDirectors`, функции приглашений |
| `src/menu.js` | `/menu`: у HR — «Добавить нового сотрудника», «База знаний» (добавить / удалить файл), «Обращения (N)»; у сотрудника — «Мои обращения» |
| `src/invite.js` | `/cancel`; добавление сотрудника для HR (опрос, приглашение, QR); активация сотрудника по QR |
| `src/support.js` | обращения сотрудник ↔ HR: создание тикета, чат, списки, карточки, закрытие, архив, пересылка вложений |
| `src/tickets.js`, `src/mongo.js` | тикеты в MongoDB: схема, атомарные операции, списки; подключение и индексы |
| `src/phone.js` | нормализация телефона, проверка почты |

| `src/kafka.js` | продюсер; `sendHrAnswer` -> `onboarding.answers` (пока не вызывается) |
| `src/knowledge.js` | база знаний для HR: загрузка (файл из чата -> S3 -> `POST /v1/documents` -> уведомление) и удаление (список кнопками -> подтверждение -> `DELETE /v1/documents/{имя}` -> уведомление) |
| `src/ml.js` | HTTP-клиент ML: `ask` -> `/v1/ask`; `addDocument`, `listDocuments`, `deleteDocument` -> `/v1/documents`; `ticketTitle` -> `/v1/ticket-title` |
| `src/s3.js` | `putFile` / `getFile` / `deleteFile` в бакете |

Команды: `/start`, `/id` (свой `max_id`), `/menu` (интерактивное меню, см. `menu.js`; выводит из чата с HR / ответа в тикет), `/cancel`,
`/bot` (выйти из чата с HR или из тикета).

**Обращения к HR (тикеты).** Закреплённый HR сотрудника — автор его приглашения (`users.hr_id`). Нет HR — бот отказывает, тикет не создаётся.
- Сотрудник: под каждым ответом RAG (`code 200`, а также при недоступном ML) — кнопка «Связаться с HR» (`tk:ask:<id>`; вопрос и ответ лежат
  в Redis `lastqa:<max_id>:<id>` 7 дней, `GETDEL` — второе нажатие тикет не дублирует). При `code 400` бот показывает текст сценария «посоветуюсь с коллегами» (картинка 13) с кнопками «Передать вопрос в отдел подбора персонала» (эта кнопка создаёт тикет) и «Связаться с рекрутером»; автотикета больше нет.
  Тикет начинается с вопроса и ответа бота; сотрудник сразу входит в чат с HR (шаг `ticket_chat`): текст, фото, файлы уходят в тикет и HR.
  Выход — «Вернуться к боту» / `/bot` / `/menu`. Ответ HR приходит «HR по №N «тема»: …» с кнопками «Ответить» (войти в чат по этому тикету)
  и «Вопрос решён» (закрыть). `/menu` -> «Мои обращения»: открытые и архив, карточка с историей.
- HR: уведомление о новом тикете и о новом сообщении с кнопкой «Открыть»; `/menu` -> «Обращения (N)»: открытые тикеты, сначала
  с непрочитанными (`●N`), затем по последнему сообщению, по 10 на страницу; «Архив» — закрытые. `hr` видит тикеты своих сотрудников, `hr_head` — все.
  Карточка: шапка (№, тема, категория, сотрудник, тег, руководитель, как создан), последние 10 сообщений (длинные обрезаются, всё — в пределах 4000 символов),
  кнопки «Закрыть», «След. непроч. →», «← К обращениям»; в архиве — «Переоткрыть». Открытая карточка = активный тикет (шаг `ticket_reply`):
  всё, что HR пишет, уходит сотруднику, бот подтверждает «→ №N, Имя Ф.». Пока HR в тикете, новые сообщения сотрудника приходят без уведомления.
- Тема: сначала первые 60 символов вопроса, в фоне `POST /v1/ticket-title` (LLM) заменяет её на тему из 3–6 слов и категорию; без LLM остаётся временная.
- Закрыть может HR или сотрудник, вторая сторона получает уведомление; сообщения в закрытый тикет не принимаются.
- Вложения пересылаются по `token` исходного вложения; если MAX не принял — бот скачивает по `url` и загружает заново; иначе текст с пометкой.
  В истории тикета — только тип и имя вложения.

**Документ в базу знаний.** `/menu` -> «База знаний» -> «Добавить файл» (шаг `kb_await_file`) -> HR присылает файл (PDF, TXT, MD, до 50 МБ).
Бот сразу отвечает «принят», а дальше в фоне: скачивает файл из MAX, кладёт в S3 `incoming/<uuid>/<имя>`, вызывает `POST /v1/documents`
и присылает HR уведомление: «добавлен/обновлён, фрагментов: N» или причину ошибки. Фоном — потому что polling библиотеки ждёт обработчики,
и индексация (минуты) иначе заблокировала бы бота для всех. При ошибке входящий файл удаляется из S3. Имя файла — имя документа в базе,
одноимённый заменяется. Таймаут индексации 30 мин (`ML_INDEX_TIMEOUT_MS`); запрос идёт через `node:http`, т.к. у `fetch` свой лимит 5 мин.

**Удаление документа.** `/menu` -> «База знаний» -> «Удалить файл» -> бот берёт список у ML (`GET /v1/documents`) и показывает кнопки
по 10 на страницу (← / →, «Отмена»); имена хранятся в состоянии `kb_delete_pick`, в кнопке только индекс (`kbdel:<i>`).
Выбор -> подтверждение «Удалить / Отмена» (`kb_delete_confirm`) -> бот сбрасывает шаг (повторное нажатие ничего не делает) и в фоне
вызывает `DELETE /v1/documents/{имя}`, затем уведомляет HR («удалён», «уже нет в базе» или «сервис недоступен»).
Файл удаляется из S3, `knowledge_base.json` и Chroma. Права и шаг проверяются на каждой кнопке.

**Добавление сотрудника.** `/menu` -> «Добавить нового сотрудника» -> имя -> фамилия -> тег (кнопки) -> руководитель (кнопки) -> почта -> телефон ->
подтверждение. Бот создаёт запись в `invites` и присылает HR QR-код (PNG, загружается в MAX) со ссылкой
`https://max.ru/<username_бота>?start=<токен>`. Токен: 24 случайных байта, в БД только sha256-хэш,
срок 7 дней, одноразовый. Новое приглашение на тот же номер гасит предыдущее. Нельзя создать приглашение на номер, который уже есть в `users`.
Если загрузка картинки в MAX не удалась, она повторяется до 3 раз; если не помогло, HR получает только ссылку (приглашение не теряется). Сбои логируются: `qr upload failed (attempt N/3)`.

**Активация.** Сотрудник сканирует QR -> бот (событие `bot_started` с payload или `/start <токен>`) просит нажать
«Поделиться контактом». Проверки: контакт принадлежит самому отправителю (`max_info.user_id`), номер из контакта
равен номеру, введённому HR. До 5 неудачных попыток. При успехе создаётся `users` (роль `employee`, поля из приглашения),
приглашение гасится, HR получает уведомление. Всё в одной транзакции.

Шаги диалога (`add_*`, `await_contact`, `kb_*`, `ticket_chat`, `ticket_reply`) хранятся в Redis и переживают рестарт бота.
Самостоятельной регистрации нет. Неизвестному пользователю бот предлагает обратиться к HR.
Права на «Добавить нового сотрудника» проверяются при показе меню, при нажатии кнопки и на каждом шаге опроса.

Поток: `/start` ищет пользователя по `max_id` (нет в БД — предлагает обратиться к HR), ставит шаг `idle`.
Обычное текстовое сообщение зарегистрированного пользователя:
1. роль `employee` — это вопрос (если сотрудник не в чате с HR): бот вызывает `POST /v1/ask` с `user_id = users.id` и отправляет пользователю `answer`
   (текст формирует ML; при `code 200` — с кнопкой «Связаться с HR», при `code 400` — текст сценария с двумя кнопками, без автотикета); техническая ошибка или таймаут -> «Сервис ответов временно недоступен» (тоже с кнопкой «Связаться с HR»),
   подробности в `docker compose logs bot` (`ml api failed`). Вызов ML и ответ идут в фоне (`answerInBackground` в `index.js`, пока LLM думает — индикатор «печатает»), иначе polling ждёт обработчик и бот замирает для всех. Настроение по вопросу ML считает сам, в фоне;
2. другие роли получают подсказку «Откройте /menu».

TLS: библиотека ходит на `platform-api2.max.ru`, сертификат подписан российским УЦ Минцифры
(Russian Trusted Root CA), которого нет в стандартных хранилищах. Корневой сертификат лежит в
`bot/certs/russian_trusted_root_ca.pem` (источник: gu-st.ru, SHA-256 `D2:6D:2D:02:...:CF:31`, до 2032)
и подключён в Dockerfile через `NODE_EXTRA_CA_CERTS` (только для процесса бота).
При запуске с хоста: `NODE_EXTRA_CA_CERTS=bot/certs/russian_trusted_root_ca.pem npm run dev`.

Запуск: `docker compose up -d --build bot` (после правок кода бота нужна пересборка). Логи: `docker compose logs bot`. Локально: `cd bot && npm install && npm run dev`
(с хоста нужны `BOT_TOKEN` и порты из `.env`; дефолты в `config.js` под `localhost`).

## Переменные окружения (`.env`)

`BOT_TOKEN` (токен бота из MAX, обязателен), `POSTGRES_USER/PASSWORD/DB/PORT`, `REDIS_PORT`, `S3_IMAGE`, `S3_ROOT_USER`,
`S3_ROOT_PASSWORD`, `S3_BUCKET`, `S3_API_PORT`, `S3_CONSOLE_PORT`,
`KAFKA_EXTERNAL_PORT`, `KAFKA_TOPIC_ANSWERS`, `ML_PORT`, `MENO_MODEL` (модель для Ollama),
`MONGO_PORT`, `MONGO_DB`, `MONGO_ROOT_USER`, `MONGO_ROOT_PASSWORD`, `MONGO_APP_USER`, `MONGO_APP_PASSWORD`.
В контейнер бота compose передаёт `ML_API_URL=http://ml:8000` и `ML_TIMEOUT_MS=90000` (`ML_INDEX_TIMEOUT_MS` — по умолчанию 30 мин). Остальные настройки ML (`RAG_TOP_K`, `EMBED_MODEL`,
`LLM_TIMEOUT`, `CHUNK_SIZE` и т.д.) — переменные окружения из `ml/app/config.py`, при необходимости добавляются в `environment` сервиса `ml`.

Значения паролей в `.env.example` — заглушки, перед реальным использованием заменить.
