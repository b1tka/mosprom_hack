# hr_analytics — отчёты по онбордингу и рассылка через Яндекс Почту

Сервис раз по расписанию собирает аналитику по новым сотрудникам и рассылает **личные отчёты по ролям** из ТЗ:

| Роль (`role.name`) | Отчёт | По умолчанию |
|---|---|---|
| `hr` — HR-менеджер | Сводка по всем новичкам: красные флаги, тональность, темы трудностей, этапы, динамика, таблица новичков по приоритету | будни, 09:00 |
| `director` — руководитель подразделения | Только **его** новички: статус каждого, «кого пора встретить лично» (рекомендация со сроком), настроение по сотрудникам | понедельник, 09:00 |
| `hr_head` — руководитель по подбору и развитию | Дайджест «Настроения в коллективе новичков»: зоны риска, кластеры тем, разрез по подразделениям (`tag`) и руководителям, красные флаги | понедельник, 09:00 |

Письмо — HTML (графики встроены, работает в Яндекс Почте web/мобильной) + PDF во вложении. Новый сотрудник (`employee`) отчётов не получает.

## Откуда данные
- **MongoDB** — статистика настроения: одна запись на сотрудника в коллекции `MONGO_STATS_COLLECTION` (по умолчанию `stats`).
  Понимается формат ML-сервиса (`uid, stage, total_requests, moods{}, reasons{}, red_flag, last_reason`) и старый формат ветки
  hr_analytics (`request_count, mood, request_tags, reason`); идентификатор — `MONGO_UID_FIELD` → `uid` → `user_id` → `_id`.
  Если задать `MONGO_EVENTS_COLLECTION` (история `{uid, ts, mood, reason, urgent}`), в отчётах появятся графики динамики по неделям.
- **PostgreSQL** — ФИО, роль, подразделение (`tag`), руководитель (`director_id`) и **e-mail получателя** (`users.email`).
  Без e-mail отчёт пропускается (в логе предупреждение).
- `stage = null` обрабатывается штатно: колонка и график этапов скрыты, вместо них короткая пометка; как только ML начнёт отдавать этап — появятся сами.

> ⚠ В переданном `main` коллекции Mongo ещё не описаны (ML пишет статистику в Redis). Схема документа выше — **предположение по формату ML**.
> Если в Mongo лежит иначе — правится только `normalize_stats()` / `normalize_event()` в `app/sources/mongo.py`.

## Быстрый старт
```bash
cd hr_analytics
pip install -r requirements.txt
cp .env.example .env                      # заполнить DATABASE_URL, MONGO_URL, SMTP_*

python -m app preview --demo              # без баз: HTML+PDF на демо-данных -> reports/  (примеры уже в examples/)
python -m app check                       # проверка PostgreSQL, MongoDB и входа в SMTP
python -m app preview                     # то же на реальных данных, ничего не отправляя
python -m app send --to me@yandex.ru      # боевые отчёты, но все письма на ОДИН адрес (тема с [TEST])
python -m app send --role hr              # реальная рассылка одной роли
python -m app schedule                    # постоянный процесс по расписанию
python -m unittest discover -s tests -v   # тесты (без баз и почты)
```

## Яндекс Почта
1. Ящик-отправитель: Настройки → Почтовые программы → включить доступ по протоколу SMTP.
2. https://id.yandex.ru/security/app-passwords → создать пароль приложения для «Почты» → `SMTP_PASSWORD`.
   Пароль от аккаунта не подойдёт (включённая 2FA или нет — Яндекс требует пароль приложения для SMTP).
3. `SMTP_USER` — полный адрес; адрес «От» всегда равен ему (требование Яндекса).
4. Сервер `smtp.yandex.ru`, порт 465/SSL (или 587 + `SMTP_SECURITY=starttls`). Между письмами пауза `SMTP_PAUSE_SEC`
   (у Яндекса лимиты на частоту), ошибка одного письма не прерывает остальные, сетевые сбои — 3 повтора.

## Docker
`docker-compose.hr-analytics.yml` — готовый блок сервиса для корневого compose (подключается к postgres и mongo в сети проекта):
```bash
docker compose -f docker-compose.yml -f hr_analytics/docker-compose.hr-analytics.yml up -d --build hr-analytics
```
Для проверки на живой базе: `mock/seed_users.sql` (пользователи в Postgres) и `python mock/seed_mongo.py` (статистика в Mongo).

## Как считается
- **Индекс настроения** 0–100 = среднее по сообщениям: позитив 100, нейтрально 60, негатив 25, критично 0.
- **Риск сотрудника**: *высокий* — красный флаг или есть «критическое» сообщение; *повышенный* — ≥3 сообщений и ≥40% негатив/критика;
  *норма*; *нет данных* — обращений не было. Пороги — в `app/analytics.py::assess_risk`.
- Главная тема — самая частая из «проблемных» (доступы, конфликты, нагрузка, отпуска, зарплата, документы).

## Структура
```
app/sources/   mongo.py (статистика) · postgres.py (люди) · demo.py
app/analytics.py  метрики           app/reports.py  отчёты по ролям (модель секций)
app/charts.py     графики           app/render_html.py + templates/  письмо
app/render_pdf.py PDF               app/mailer.py   SMTP Яндекс
app/service.py    загрузка → отчёты → письма   app/scheduler.py  cron   app/cli.py  команды
```
Отчёт описывается один раз (`app/document.py`), а HTML, PDF и текстовая версия письма рендерятся из него — цифры везде совпадают.
