# CLAUDE.md

Бот для мессенджера MAX: онбординг нового сотрудника в компанию. Отвечать на русском.

## Статус
Инфраструктура в Docker, работающий бот (`bot/`, JS, `@maxhub/max-bot-api`) и ML-сервис (`ml/`, FastAPI): RAG по базе знаний и оценка настроения — код ML-команды, перенесён из веток `ml_ai`/`mood_find`. ML-разработка дальше — в `ml/` от `main`.
Готово и закоммичено: добавление сотрудника HR-ом через QR; ответы сотруднику из RAG; HR в `/menu` добавляет и удаляет файлы базы знаний.
Написано, но НЕ проверено и НЕ закоммичено: обращения сотрудник ↔ HR (тикеты в MongoDB, `support.js`). Следующий шаг — проверить на моках (как проверяли приглашения и базу знаний), потом коммит по команде пользователя.
Проект развёрнут пользователем на VPS (там же LLM); на dev-ноутбуке LLM нет. Деплой — раздел «Деплой на VPS» ниже в этом файле.
Сценарий онбординга по ТЗ (`Финал. ТЗ. Чат-бот Корсик- 15.09.xlsx`) реализован: `bot/src/scenario/scenario.yaml` + `bot/src/onboarding/` (подробно — раздел «Сценарий онбординга — детали» ниже); миграция `db/migrations/004_onboarding.sql` применяется ДО пересборки бота.
Стек для экспертов: `INFRASTRUCTURE.md`; служебная справка — ниже. Документация MAX для JS: https://dev.max.ru/docs/chatbots/bots-coding/js

## Стек
- Postgres 16 — `users` (`hr_id` — закреплённый HR), `role`, `tag`, `invites` (`db/init/*.sql` выполняются только при первом старте тома; для живой БД — `db/migrations/`, вручную).
- MongoDB 7.0 (`mongo:7.0.41`; 8.x не использовать: на ядре Linux 6.19–7.0.13 `mongod` 8.0.28+ не стартует, у 7.0 другой TCMalloc, проверки нет) (на хосте порт 27018; 27017 занят локальным MongoDB) — обращения сотрудников к HR: коллекции `tickets` (тикет с перепиской) и `counters` (номер тикета), пишет бот. Пользователь приложения с `readWrite` на базу `onboarding` (`db/mongo-init/`), сервисам передаётся `MONGO_URL`.
- Redis 7 (на хосте порт 6380) — состояние диалогов бота (`dialog:<max_id>`), переживает рестарт.
- S3 — OpenMaxIO (форк консоли MinIO), образ `ghcr.io/snazy/maxio-release` (неофициальный; MinIO на Quay/Docker Hub не скачался). Бакет `onboarding-files`.
- Kafka (KRaft, 1 нода) — топик `onboarding.answers`, два вида сообщений -> `ml-mood-consumer` -> настроение: (1) ответ сотрудника на вопрос HR `{uid, hr_question, answer, stage}` (бот: `sendHrAnswer`, опросы HR ещё не сделаны); (2) `{type: "ticket", uid, ticket_number, closed_at, messages[]}` — полный диалог тикета при его закрытии (бот: `sendTicketDialog`, вызывается из `support.js`), один вердикт на диалог. Топик `onboarding.alerts`: срочная оценка (`urgent`) -> ML (`app/alerts.py`) -> `{type: "red_flag", uid, source, ticket_number?, reason, explanation, text?}` -> консьюмер бота (`alerts.js`) -> уведомление закреплённому HR (нет `hr_id` — всем `hr`/`hr_head`), не чаще раза в час на сотрудника (Redis `alert:<uid>`); кнопки «Открыть обращение» и «Флаг обработан» (`rf:reset:<uid>` -> Mongo `stats.red_flag=false`).
- ML — `ml/` (Python 3.12, FastAPI, порт 8000; один образ: `ml` API и `ml-mood-consumer`). `POST /v1/ask {user_id: users.id, question, stage}` -> HTTP 200 `{code: 200|400, answer}`, 503 — LLM/база недоступны. RAG: Chroma (том `ml_data`) + эмбеддинги e5-large + LLM meno-lite-0.1 в `ollama` (compose-профиль `llm`). Документы базы знаний — в S3 `knowledge/`, индексация `python -m app.ingest`. Статистика настроения — Mongo: `stats` (сводка на сотрудника, `uid` = users.id) и `events` (история оценок, `event_key` защищает от дублей). `POST /v1/documents {key: incoming/<id>/<имя>}` — добавить документ из S3 в базу (переносит в `knowledge/`); `GET /v1/documents` — список; `DELETE /v1/documents/{имя}` — удалить из S3, JSON и Chroma; `POST /v1/ticket-title {text}` — тема и категория тикета (LLM). Контракт — `ml/README.md`.
- Тестовая админка `admin/` (FastAPI + Jinja2 + HTMX, профиль compose `admin`, порт только 127.0.0.1 через SSH-туннель; ТОЛЬКО для тестирования, показывает ПДн и даёт полный доступ к базам): вход по коду из бота (`/admin`, режим `ADMIN_ACCESS=off|hr|anyone`), разделы — обзор/статус, сотрудники, тикеты, база знаний, базы данных (Postgres/Mongo/Redis/Kafka/S3, опасные операции требуют слова `ПОДТВЕРЖДАЮ`), журнал `admin_audit`. Действия над тикетами идут через внутренний HTTP бота (`bot/src/internal.js`, порт 3001 только в сети compose). Подробности и как убрать — раздел «Тестовая админка» ниже.
- Добавление сотрудника из PDF: HR присылает PDF боту (или `/menu` -> «Добавить сотрудника из PDF»), ML `POST /v1/users/extract` (`ml/app/users.py`, модуль из ветки `pdf_user_load`) достаёт имя, фамилию, почту, телефон, тег и руководителя, бот (`pdfusers.js`) подставляет их в обычную форму добавления, HR подтверждает.
- Бот — `bot/src`: `index.js` (точка входа, `/start`, `/id`; сообщения сотрудника `employee` -> `POST /v1/ask` через `ml.js`, ответ — текст от ML + кнопка «Связаться с HR», при `code 400` — текст сценария «посоветуюсь с коллегами» + кнопки «передать вопрос»/«связаться», без автотикета), `menu.js` (`/menu`: HR — добавить сотрудника / База знаний / Обращения; сотрудник — Мои обращения), `support.js` + `tickets.js` + `mongo.js` (тикеты сотрудник ↔ закреплённый HR: чат `ticket_chat` / ответ HR `ticket_reply`, `/bot` — выход, архив, вложения), `invite.js` (`/cancel`, добавление сотрудника, активация по QR), `knowledge.js` (HR в `/menu`: добавить файл -> S3 `incoming/` -> `/v1/documents` в фоне -> уведомление; удалить файл -> список кнопками -> подтверждение -> `DELETE` в фоне -> уведомление), `scenario/` (scenario.yaml, load.js, schedule.js) и `onboarding/` (engine.js, register.js, send.js, store.js, notify.js, mailer.js) — сценарий онбординга, `alerts.js` (алерты red_flag), `admin.js` + `internal.js` (вход в админку и её внутренний API), `errorlog.js`, `ui.js`, `db.js`, `state.js`, `kafka.js`, `s3.js`, `phone.js`, `config.js`.

## Команды
```bash
cp .env.example .env               # один раз, поменять пароли, указать BOT_TOKEN
docker compose up -d
docker compose ps -a
docker compose up -d --build bot   # после любых правок кода бота
docker compose --profile llm up -d # вместе с LLM (нужно >= 12 ГБ RAM; на dev-ноутбуке НЕ запускать)
docker compose up -d --build ml ml-mood-consumer   # после правок ML
docker compose run --rm ml python -m app.ingest build --from-s3   # пересобрать базу знаний из S3
docker compose run --rm --no-deps ml python -m unittest discover -s tests -v
docker compose logs bot
docker compose down -v             # сброс данных, init-скрипты БД выполнятся заново
```
Адреса внутри сети compose: `postgres:5432`, `mongo:27017`, `redis:6379`, `s3:9000`, `kafka:9092`, `ml:8000`, `ollama:11434`. С хоста: Kafka `localhost:29092`, Redis `localhost:6380`, MongoDB `localhost:27018`, ML `localhost:8000`.

## Доменная модель
- Роли: новый сотрудник (`employee`), руководитель подразделения (`director`), HR-менеджер (`hr`), руководитель по подбору и развитию персонала (`hr_head`). Слаги — предположение, в UML были только `employee | director`.
- Теги (GTP, GrPP, Luzhniki) только у нового сотрудника, у остальных ролей `tag_id` пуст. БД это не проверяет — контролировать в коде.
- У руководителя может быть много новых сотрудников, у сотрудника один руководитель (`users.director_id`, NULL у руководителей).
- `users.max_id` — id пользователя в MAX, уникален. `users.email`, `users.phone` необязательные.

## Как появляются сотрудники
Самостоятельной регистрации нет. `hr` и `hr_head` в `/menu` выбирают «Добавить нового сотрудника», заполняют данные и получают QR (ссылка `max.ru/<бот>?start=<токен>`, 7 дней, одноразовая, в БД только хэш). Сотрудник сканирует QR и жмёт «Поделиться контактом»: контакт должен быть его собственным, а номер — совпасть с введённым HR. Только после этого создаётся `users` (роль `employee`). Директоров, HR и `hr_head` добавляют вручную в БД.

## Заметки
- `.env` в `.gitignore` (там токен бота и пароли); пароли в `.env.example` — заглушки. Токен не коммитить и не выводить в логи.
- MAX API (`platform-api2.max.ru`) подписан УЦ Минцифры: корневой сертификат в `bot/certs/`, подключён через `NODE_EXTRA_CA_CERTS` в Dockerfile.
- На хосте уже есть локальный Redis с паролем на 127.0.0.1:6379 — поэтому наш проброшен на 6380.
- Библиотека MAX скрывает причину сетевых ошибок загрузки («Network error»), при сбоях смотреть `docker compose logs bot`.
- Коммит и пуш — только по явной команде пользователя, без строки `Claude-Session`. Роль Евгения (`hr`) для тестов не менять: функции `employee` проверяет второй человек.
- Большие фичи: сначала подробные уточняющие вопросы и итоговый план, реализация — после «утверждаю». Проверки — моками бота/ctx поверх живых Postgres/Redis/Mongo/S3/ML; тестовые данные после проверки удалять.
- Отложено (пользователь не выбрал, может вернуться): проставить `hr_id` старым сотрудникам из `invites.created_by`, оценка после закрытия тикета; `ENV PYTHONUNBUFFERED=1` в `ml/Dockerfile` (сейчас `print` индексации в логах `ml` появляется с задержкой).
- Docker на dev-ноутбуке иногда перезапускается и оставляет `mongo` / `ml-mood-consumer` в `Exited` — проверять `docker compose ps -a` и поднимать.
- LLM на этом ноутбуке не запускать (8 ГБ на Docker, нужно >= 12): работать без профиля `llm`; после проверок модель не оставлять запущенной. Запуск планируется на другой машине.
- Настроение пишется в Mongo (`stats` + `events`, `STORE_BACKEND=mongo`), а не в Redis. `hr_analytics/` (отчёты на почту, из ветки `mood_find`) влит в `main`, читает эти коллекции; сервис `hr-analytics` в профиле compose `reports` (`docker compose --profile reports up -d --build hr-analytics`), пока `REPORT_RECIPIENT_OVERRIDE` задан, все письма идут на один адрес. Получатели — `users.email` (у HR/директоров пусто, заполнять вручную).
- База знаний проиндексирована (146 чанков в томе `ml_data`, PDF в S3 `knowledge/`). Без LLM `/v1/ask` отдаёт 503 — это ожидаемо на dev-ноутбуке.
- В shell задан `http_proxy`: для `curl localhost:...` нужен `--noproxy '*'`, иначе ответ 503 от прокси.
- В живом MAX не проверено: ответы на вопросы сотрудника, формат deep-link со `start`, кнопка «Поделиться контактом», показ QR. Загрузку файла HR-ом пользователь подтвердил на VPS («всё работает»).
- Тикеты (обращения к HR) написаны, но ещё не проверялись ни на моках, ни в MAX; миграция `db/migrations/003_users_hr.sql` к живой БД не применена (на VPS тоже применить вручную).
- Долгие операции в обработчиках бота (индексация документа) — только в фоне: polling библиотеки ждёт все обработчики пачки, иначе бот замирает для всех. Список — в «Бэклог» ниже.

# Служебная справка (перенесено из INFRASTRUCTURE.md)

`INFRASTRUCTURE.md` описывает стек для экспертов. Всё операционное — деплой, админка, детали сценария и бота, статус проверок, бэклог — лежит здесь.

## Деплой на VPS
Пользователь развернул стек на VPS (с профилем `llm`). Свежие тома там пустые, поэтому после первого `up` нужно:
1. **Код:** `git pull && docker compose up -d --build ml bot` (после правок бота / ML).
2. **Миграции** (для БД, созданной до них; по порядку, каждую один раз):
   `docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < db/migrations/<файл>.sql`.
   Применять ДО пересборки бота, если новый код пишет в новые столбцы (например, `003_users_hr.sql` — без неё активация QR падает).
3. **HR-пользователь** (бот создаёт только `employee`; `max_id` — команда `/id` в боте):
   ```sql
   INSERT INTO users (name, surname, role_id, max_id)
   SELECT 'Евгений', 'Мерескин', id, 385032755 FROM role WHERE name = 'hr'
   ON CONFLICT (max_id) DO UPDATE SET role_id = EXCLUDED.role_id;
   ```
   Удобнее вставлять в интерактивный `psql` (`docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'`): многострочный heredoc при копировании в терминал зависал на `heredoc>`.
4. **База знаний:** без неё `/v1/ask` -> 503 «Векторная база пуста». PDF лежат в ветке `mood_find`:
   `git archive origin/mood_find data | tar -x` -> `docker compose run --rm -v "$PWD/data":/import ml python -m app.ingest upload /import`
   -> `docker compose stop ml && docker compose run --rm ml python -m app.ingest build --from-s3 && docker compose up -d ml` (~11 мин на CPU). Дальше документы добавляет HR через бота.
5. **Диагностика:** «Сервис ответов временно недоступен» у сотрудника = ML ответил ошибкой; причина — в `docker compose logs ml` (`Ошибка RAG` + traceback: пустая база, нет `ollama`, модель не скачана, таймаут). Ход индексации — `docker compose logs -f ml`.
6. **MongoDB только 7.0.** `mongod` 8.0.28+ / 8.3 не стартует на ядре Linux 6.19–7.0.13 (`MongoDB cannot start: ... known incompatibility`, SERVER-121912): в 8.x вшит Google TCMalloc (rseq), в 7.0 — gperftools, проверки нет. Не менять образ на `mongo:8`/`latest`. Том от 8.0 версия 7.0 не откроет: `docker compose down mongo && docker volume rm <проект>_mongo_data` (данных там пока нет), затем `docker compose up -d mongo`.
7. **Смоук после деплоя:** `./scripts/smoke.sh` (`--no-llm` — без проверок модели, `--keep` — не удалять тестовые данные). Проверяет контейнеры, схему Postgres (миграции), версию Mongo, Redis/Kafka/S3, ML API, а с LLM — `/v1/ask`, `/v1/ticket-title`, запись оценки в `stats`/`events` и путь «диалог тикета -> Kafka -> консьюмер -> events»; затем логи бота и `hr-analytics check`. FAIL — стек неисправен (код выхода 1), WARN — обратить внимание (SMTP не настроен, пустая база знаний, LLM оценила мягче). Тестовый uid `00000000-0000-4000-8000-0000000005a0`, его записи в Mongo удаляются.

Сценарий онбординга: миграцию `004` применить ДО пересборки бота (бот читает `users.start_date`), затем `docker compose up -d --build bot` (в образ добавлены `assets/`, зависимости `yaml`, `nodemailer`). Сотрудников, заведённых раньше, запускает HR кнопкой «Запустить сценарий» или админка.

## Тестовая админка
Веб-интерфейс для **тестирования**: обзор системы, сотрудники и настроение, обращения, база знаний, управление базами. В проде не предполагается: показывает персональные данные и переписку, SQL-консоль и редакторы дают **полный доступ к данным**.

**Включение**
1. В `.env`: `ADMIN_ACCESS` (`off` — выключена, `hr` — код входа только для `hr`/`hr_head`, `anyone` — любому, кто написал боту `/admin`), `SESSION_SECRET` и `ADMIN_API_TOKEN` (случайные строки: `openssl rand -hex 32`), при необходимости `ADMIN_URL`, `ADMIN_PORT`.
2. `docker compose --profile admin up -d --build admin bot` (бот нужен: выдаёт коды и выполняет действия над тикетами).
3. С компьютера: `ssh -L 8080:localhost:8080 <vps>`, открыть http://localhost:8080. Порт публикуется строго на `127.0.0.1` (в compose зашито).
4. Вход: написать боту `/admin`, ввести код (8 символов, 5 минут, одноразовый) или открыть ссылку из сообщения. Сессия 12 часов, cookie `HttpOnly`, `SameSite=Strict`. Десять неверных кодов с одного адреса блокируют вход на 10 минут.

**Разделы**
- *Обзор*: состояние Postgres, Mongo, Redis, Kafka (лаг групп), S3, ML, LLM, бота; счётчики; красные флаги; настроение за 7 дней; последние ошибки бота (`console.error` -> Redis-список `bot:errors`, последние 100).
- *Сотрудники*: список с риском и индексом настроения (`hr_analytics/app/analytics.py`), карточка с динамикой и тикетами; действия: снять красный флаг, закрепить HR, изменить email.
- *Тикеты*: фильтры, поиск, переписка; ответить, закрыть, переоткрыть (через **внутренний HTTP бота** `bot:3001`, секрет `ADMIN_API_TOKEN`, порт не публикуется), переназначить HR.
- *База знаний*: список, загрузка (S3 `incoming/` -> `POST /v1/documents` в фоне), удаление, тестовый вопрос к RAG от uid `00000000-0000-4000-8000-0000000000ad`.
- *Базы данных*: Postgres (таблицы, поиск, правка/удаление строк по PK, SQL-консоль), Mongo (коллекции, фильтр JSON без `$where`, редактор, вставка, удаление), Redis (поиск по маске, значения; сессии и коды скрыты), Kafka (только чтение), S3 (список, скачивание, удаление).
- *Онбординг*: шаги и состояние, ответы опросов, «выполнить следующий шаг сейчас», «▶ Выполнить» у любого шага (с начала, ответы и ожидания шага сбрасываются), сдвиг будущих шагов на N дней, пауза, пересчёт даты, запуск и сброс — так проверяются 3 месяца сценария за минуты.

**Безопасность.** Изменение/удаление в базах и любой изменяющий SQL требуют слова `ПОДТВЕРЖДАЮ`; удаление коллекции Mongo — ещё и её имени. Изменяющие запросы защищены CSRF-токеном, принимается только `Host: localhost|127.0.0.1` (защита от DNS-rebinding), без `SESSION_SECRET` от 32 символов сервис не стартует. Каждое действие пишется в Mongo `admin_audit` (SQL до 2000 символов). Подтверждение защищает от случайного клика, не от умысла: SQL-консоль выполняет любой запрос с правами пользователя Postgres из `.env`.

**Как убрать.** `docker compose --profile admin down`, в `.env` `ADMIN_ACCESS=off` (или удалить `ADMIN_*`, `SESSION_SECRET`), пересоздать бота (`docker compose up -d bot`): `/admin` ответит «Админка отключена», внутренний API не поднимется без `ADMIN_API_TOKEN`. Полное удаление: каталог `admin/`, сервис `admin` в `docker-compose.yml`, `bot/src/admin.js`, `bot/src/internal.js` и подключение в `bot/src/index.js`.

**Проверка.** Юнит-тесты (после `docker compose --profile admin build admin`): `docker run --rm -v "$PWD/admin/tests:/srv/tests:ro" -e ADMIN_ACCESS=anyone -e SESSION_SECRET=$(openssl rand -hex 32) onboarding-admin python -m unittest discover -s tests`. `./scripts/smoke.sh` при запущенной админке проверяет loopback-порт, вход по коду и все разделы.

## Сценарий онбординга («Корсик») — детали
Бот ведёт сотрудника по ТЗ (`Финал. ТЗ. Чат-бот Корсик- 15.09.xlsx`): знакомство до выхода, первый день по часам, 3-й день, 2 недели, 2 месяца, конец испытательного, опросы, поздравления, подборки. Вопросы боту можно задавать на любом этапе.

**Где что лежит**
- `bot/src/scenario/scenario.yaml` — весь сценарий (тексты из таблицы дословно, `Х` -> `{name}`): шаги, время, теги, картинки, кнопки, ветки. Формат — в шапке файла. Правка = правка файла + `docker compose up -d --build bot`. Ошибка в файле: бот не стартует и перечисляет все проблемы (`docker compose logs bot`).
- `scenario/load.js` (проверка и компиляция), `schedule.js` (расписание), `bot/src/onboarding/` (движок, планировщик, отправка, уведомления HR).
- `bot/assets/photos/<N>.jpg` — «Изображение N» из ТЗ. `bot/assets/content/` — необязательные вложения (PDF, презентация, открытки); нет файла — сообщение уходит без него.
- Mongo: `onboarding` (план шагов и состояние диалога), `survey_answers` (все ответы). Postgres: `users.start_date`, `invites.start_date` (миграция `004`).

**Расписание.** От QR: дата выхода = дата генерации QR + 3 дня (выходной -> понедельник), хранится в приглашении и копируется в `users.start_date`. Часовой пояс Москва (+3). Рабочие дни Пн–Пт без праздников; «второй/третий рабочий день» — по будням; «через 10 дней», «через 2 недели» — календарно (выходной -> понедельник); «первый день второго месяца» = выход + 1 мес.; «+1 мес. 2 нед.», «+1 мес. 3 нед.», «+2 мес. 2 нед.»; «последний день испытательного» = выход + 3 мес. − 1 день (выходной -> пятница). Время, которого нет в ТЗ, выставлено в `scenario.yaml` (12:00 / 10:00). Активация QR запускает сценарий сразу; при поздней активации шаги с временем, ушедшим меньше чем на сутки, уходят сразу, старые пропускаются. Планировщик в процессе бота, проход каждые 30 с; состояние в Mongo, рестарт ничего не теряет и не дублирует (шаг захватывается атомарно, один шаг за раз).

**Теги.** Офис — GrPP и Luzhniki (`office_tags`), GTP — предприятие. Шаги с `tags:`/`office:` уходят только подходящим (карта территории — GTP, карта этажей — Luzhniki, «первый день позади», адаптационный план, книги — офис, спортзал — GTP, мероприятия — GrPP и Luzhniki; варианты текстов документов, транспорта, справочника, опроса).

**Вопросы и ответы.** Типы: выбор (в т.ч. «Свой вариант»), множественный выбор, шкала 1–10 (ниже 8 просит причину), да/нет с причиной, свободный текст (рассказ о себе + фото). Вопрос заменяется на «✓ ответ», повторное нажатие — «уже закрыт». «Ты/вы» запоминается (`onboarding.address`), без ответа за 12 ч берётся «ты». Опрос без ответа напоминает через сутки и ещё раз через сутки (картинка 12), затем считается просроченным. Когда бот не ждёт ответ, текст идёт в RAG; когда ждёт текст (причина, «свой вариант», рассказ) — это ответ. Кнопки работают всегда.

**HR и негатив.** Негативный ответ (`negative: true`, шкала ниже 8, «Нет» по доступам, «отстаю», «задумываюсь об уходе») сразу уходит закреплённому HR (нет — всем hr/hr_head) с кнопкой «Написать сотруднику»; причина — отдельным сообщением. Тексты ответов и причины идут в Kafka `onboarding.answers` (`hr_question` = вопрос, `answer`, `stage` по дням от выхода: `preparing_for_start_job`, `first_adaptation_days`, `beggining_of_adaptation`, `main_adaptation_part`, `completion_of_adaptation`). Кнопки: «Связаться с рекрутером» = чат с закреплённым HR (тикет), «Передать проблему в отдел подбора персонала» = бот просит описать проблему, текст становится тикетом. Команды сотрудника: `/HR`, `/Food`, `/menu`. Рассказ о себе и интерес к материалам без ответа в базе знаний уходят HR. «Да» на предложения без текста в ТЗ (транспорт, карта, спортзал) берутся из RAG по фиксированному вопросу; нет ответа — fallback, HR узнаёт об интересе. Приветственное письмо (строка 19) идёт на `users.email` через Яндекс SMTP (`SMTP_*`); без SMTP шаг пропускается с записью в лог.

**Добавление сотрудника из PDF.** HR присылает PDF (один файл — один человек). Вне шага диалога бот спрашивает «Добавить сотрудника» / «Добавить в базу знаний» / «Ничего»; кнопка в `/menu` сразу ждёт файл. Бот в фоне шлёт PDF в ML `POST /v1/users/extract`, сопоставляет тег с таблицей `tag` и руководителя с БД (по фамилии, с учётом склонений) и открывает обычную форму: известные поля пропускаются, недостающие бот спрашивает, HR нажимает «Создать». Телефон нормализуется, занятый номер останавливает добавление. Без LLM недоступно. Код: `bot/src/pdfusers.js`, `bot/src/pdfusers/match.js`.

**Меню HR «Мои сотрудники»** (`/menu`): свои сотрудники (hr_head — все) со статусом и прогрессом; карточка: изменить дату выхода (ДД.ММ.ГГГГ, расписание пересчитывается), пауза/продолжить, запустить сценарий (для заведённых до внедрения).

**Проверка.** `cd bot && npm test` (расписание, загрузчик и валидатор); `npm run test:int` (нужны Mongo и Redis, `MONGO_URL`, `REDIS_URL`): сотрудник проходит 3 месяца на поддельных часах (GrPP и GTP), негатив, причины, множественный выбор, рассказ о себе, напоминания, таймаут «ты/вы», поздняя активация, пауза, смена даты, рестарт без дублей. Живую доставку картинок и кнопок в MAX проходить руками: создать приглашение, активировать, нажимать кнопки, в админке «выполнить следующий шаг сейчас» по очереди.

## Бот — детали
Файлы `bot/src`: `index.js` (`/start`, `/id`, вопросы -> ML), `config.js` (env, дефолты под localhost), `db.js` (пул Postgres, `findUserByMaxId`, `findEmployeeContacts`, `listTags`, `listDirectors`, приглашения), `menu.js`, `invite.js`, `support.js`, `tickets.js`, `mongo.js`, `phone.js`, `state.js` (Redis `dialog:<max_id>`), `kafka.js`, `knowledge.js`, `ml.js`, `s3.js`, `alerts.js`, `admin.js`, `internal.js`, `errorlog.js`, `ui.js`, `pdfusers.js`.
Команды: `/start`, `/id`, `/menu` (выводит из чата с HR / ответа в тикет), `/cancel`, `/bot` (выйти из чата с HR / тикета).

**Тикеты.** Закреплённый HR = автор приглашения (`users.hr_id`); нет HR — отказ, тикет не создаётся.
- Сотрудник: под ответом RAG (`code 200`, и при недоступном ML) кнопка «Связаться с HR» (`tk:ask:<id>`; вопрос/ответ в Redis `lastqa:<max_id>:<id>` 7 дней, `GETDEL` — второе нажатие не дублирует). При `code 400` — текст «посоветуюсь с коллегами» (картинка 13) и кнопки «Передать вопрос…» (создаёт тикет) / «Связаться с рекрутером»; автотикета нет. Тикет начинается с вопроса и ответа бота; сотрудник входит в чат (`ticket_chat`): текст, фото, файлы уходят HR. Выход — «Вернуться к боту» / `/bot` / `/menu`. Ответ HR приходит «HR по №N «тема»: …» с кнопками «Ответить» и «Вопрос решён». `/menu` -> «Мои обращения»: открытые и архив.
- HR: уведомление о новом тикете/сообщении с «Открыть»; `/menu` -> «Обращения (N)»: сначала с непрочитанными (`●N`), затем по последнему сообщению, по 10 на страницу; «Архив» — закрытые. `hr` видит тикеты своих сотрудников, `hr_head` — все. Карточка: шапка, последние 10 сообщений (до 4000 символов), кнопки «Закрыть», «След. непроч. →», «← К обращениям»; в архиве «Переоткрыть». Открытая карточка = активный тикет (`ticket_reply`): всё, что HR пишет, уходит сотруднику («→ №N, Имя Ф.»); новые сообщения сотрудника приходят без уведомления.
- Тема: сначала первые 60 символов, в фоне `POST /v1/ticket-title` (LLM) даёт тему 3–6 слов и категорию; без LLM остаётся временная. Закрыть может HR или сотрудник, вторая сторона уведомляется; в закрытый тикет сообщения не принимаются.
- Вложения пересылаются по `token`; если MAX не принял — бот скачивает по `url` и загружает заново; иначе текст с пометкой. В истории — только тип и имя.

**Документ в базу знаний.** `/menu` -> «База знаний» -> «Добавить файл» (`kb_await_file`) -> файл (PDF, TXT, MD, до 50 МБ). Бот отвечает «принят», в фоне скачивает файл, кладёт в S3 `incoming/<uuid>/<имя>`, вызывает `POST /v1/documents`, уведомляет HR («добавлен/обновлён, фрагментов: N» или причина). Фоном — иначе polling ждёт обработчик и бот замирает. При ошибке входящий файл удаляется. Имя файла = имя документа, одноимённый заменяется. Запрос через `node:http` (у `fetch` свой лимит 5 мин).
**Удаление.** «База знаний» -> «Удалить файл» -> список от `GET /v1/documents` кнопками по 10 на страницу (имена в состоянии `kb_delete_pick`, в кнопке индекс `kbdel:<i>`) -> подтверждение (`kb_delete_confirm`) -> шаг сбрасывается (повторное нажатие ничего не делает), в фоне `DELETE /v1/documents/{имя}`, уведомление. Права и шаг проверяются на каждой кнопке.

**Добавление сотрудника.** `/menu` -> имя -> фамилия -> тег -> руководитель -> почта -> телефон -> подтверждение. Бот создаёт `invites` и шлёт QR (PNG) со ссылкой `https://max.ru/<username_бота>?start=<токен>`; токен — 24 случайных байта, в БД sha256, 7 дней, одноразовый. Новое приглашение на тот же номер гасит предыдущее; номер из `users` — нельзя. Загрузка QR повторяется до 3 раз (`qr upload failed (attempt N/3)`), иначе HR получает только ссылку.
**Активация.** QR -> `bot_started` с payload или `/start <токен>` -> «Поделиться контактом». Проверки: контакт принадлежит отправителю (`max_info.user_id`), номер равен введённому HR, до 5 попыток. Успех: `users` (роль `employee`), приглашение гасится, HR уведомляется — одна транзакция.
Шаги диалога (`add_*`, `await_contact`, `kb_*`, `ticket_chat`, `ticket_reply`) в Redis, переживают рестарт. Права проверяются при показе меню, нажатии кнопки и на каждом шаге опроса.

**Поток сообщения.** `/start` ищет пользователя по `max_id` (нет — «обратитесь к HR»), шаг `idle`. Текст `employee` (не в чате с HR) -> `POST /v1/ask` с `user_id = users.id`; ответ ML как есть (`code 200` с кнопкой «Связаться с HR»; `400` — текст сценария с двумя кнопками); ошибка/таймаут -> «Сервис ответов временно недоступен» (`ml api failed` в логах). Вызов и ответ в фоне (`answerInBackground`, индикатор «печатает»). Настроение ML считает сам, в фоне. Другие роли получают «Откройте /menu».

**TLS.** `platform-api2.max.ru` подписан УЦ Минцифры; корень в `bot/certs/russian_trusted_root_ca.pem` (gu-st.ru, до 2032), подключён через `NODE_EXTRA_CA_CERTS` в Dockerfile. С хоста: `NODE_EXTRA_CA_CERTS=bot/certs/russian_trusted_root_ca.pem npm run dev`. Локально: `cd bot && npm install && npm run dev` (нужны `BOT_TOKEN` и порты из `.env`).
